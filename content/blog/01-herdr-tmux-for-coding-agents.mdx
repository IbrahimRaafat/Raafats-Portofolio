Last month I had three Codex agents grinding through microservices in separate tmux panes. I went to make coffee. When I came back, pane 3 had been sitting for 47 minutes waiting on a `— confirm migration?` prompt I never saw. The other two had finished, but I had no idea — I was still cycling `Ctrl+B n` like a night watchman.

That night cost me real money and a deadline. It also made me realize: tmux was never built for this.

---

### Why tmux breaks with agents

`tmux` and `zellij` are Unix classics. They multiplex bytes beautifully. But they see every pane as the same thing — an opaque stream of ANSI codes. They have no idea whether an agent is shipping code, stuck on a confirmation, or done and waiting for review.

So you end up doing the agent's job for it:

* **Silent stalls** — an agent pauses for human approval and you do not notice until your wall clock says otherwise.
* **Pane roulette** — you burn half your focus just checking if things finished or looped.
* **Split fleets** — local work plus a remote GPU box means two SSH sessions, zero unified view.

I did not want a prettier wrapper. I wanted a runtime that understands agents.

---

### Meet Herdr

[Herdr](https://herdr.dev) (`herdrdev/herdr`) is an open-source terminal multiplexer written in Rust, built specifically for agentic work. The shorthand I keep hearing — *"what tmux is to shells, Herdr is to coding agents"* — is the most honest pitch for it.

It keeps what you already like (tiny Rust binary, no Electron, vi and tmux keys) and adds the layer we were missing: agent awareness.

```bash
# macOS & Linux
curl -fsSL https://herdr.dev/install.sh | sh

# Homebrew
brew install herdr

# Windows (PowerShell)
irm https://herdr.dev/install.ps1 | iex
```

---

### Seeing state at a glance

Herdr reads PTY activity and surfaces real agent state in the chrome itself:

- **🟢 Working** — actively coding, patching, or testing
- **🟡 Blocked** — needs your input or an approval
- **🔵 Done** — task complete, awaiting review
- **⚪ Idle** — standby

One look at the status bar replaces all that pane-hopping. The yellow dot alone would have saved my 47 minutes.

---

### It survives your laptop dying

Like tmux, Herdr runs a daemon. Your sessions and agent threads live on that daemon, not your terminal window. Close the laptop, kill Wi-Fi, detach — agents keep running. `herdr attach` brings you back instantly. I now kick off long runs before I leave the cafe and reattach from home without losing a line.

---

### One dashboard for every machine

Most real work is not on one box. I run light frontend scaffolds locally and heavy scrapers on a remote instance. Herdr lets you stitch local and remote SSH targets into a single dashboard. If one SSH link drops, only that machine's panes go stale — nothing else freezes.

---

### Agents can drive it themselves

This is the part that changed how I think about orchestration. Herdr exposes a socket API to its own panes, so agents can call it:

```bash
# An orchestrator spins up a worker
herdr spawn --title "unit-tests" -- npm test

# Then reads that worker's output
herdr capture --pane 2
```

Suddenly a hierarchy is possible: an architect agent breaks down a ticket, spawns workers in isolated worktrees, watches their states, and merges once every pane turns blue. I have not fully automated that loop yet — but the primitive is there, and it is the first multiplexer primitive that feels agent-native rather than human-native.

---

### Should you switch?

If you regularly run two or more coding agents at once, Herdr earns its keep on day one. The state dots and daemon alone are worth it; the socket API is upside.

If you use a single agent in one pane, stay on tmux. Herdr shines when you have a fleet to watch — and a lot to lose when one pane silently stalls.
